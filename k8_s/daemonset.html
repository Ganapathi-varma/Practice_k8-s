Kubernetes: DaemonSet

Used for monitoring — runs a pod on every server (node), scaling automatically with the number of servers

What is a DaemonSet?

  • Mainly used for monitoring — runs a monitoring/agent pod on every server (node).
  • The number of pods increases based on the servers — one pod per node, so more servers means more pods.
  • There is no replicas field set for a DaemonSet — the node/server count decides the pod count automatically.
  • When a new server (node) is added, a pod is automatically scheduled onto it.
  • When a node is removed, its DaemonSet pod is garbage-collected.
  • Can target a subset of nodes using nodeSelector / node affinity / tolerations.
  • Deployed in Kubernetes using a DaemonSet object.

Monitoring Use Cases

  • Monitoring / metrics agents on every node (Prometheus Node Exporter, Datadog agent).
  • Log collection agents per node (Fluentd, Fluent Bit, Filebeat).
  • Networking plugins / CNI (Calico, Cilium, kube-proxy).
  • Storage daemons (Ceph, GlusterFS).
  • Security & compliance agents running per node.
  • Anything that must observe or serve the node/server it runs on.
One-line answer for interview: A DaemonSet is used for monitoring: it runs a copy of a pod on every server (node). The pod count increases with the number of servers, and there is no replicas field — the node count decides how many pods run.

Key behaviors

  • DaemonSet pods are scheduled by the DaemonSet controller to honor every eligible node.
  • Use tolerations so pods can also run on tainted nodes (e.g. control-plane nodes).
  • Use nodeSelector or affinity to restrict to a subset of nodes (e.g. only GPU nodes).
  • Supports rolling updates via updateStrategy: RollingUpdate.
Remember: Deployment = many interchangeable stateless pods · StatefulSet = ordered pods with identity + storage · DaemonSet = exactly one pod per node for node-level work.

DaemonSet YAML Example

A node-level log collector running on every node

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd-logger
  namespace: logging
spec:
  selector:
    matchLabels:
      app: fluentd-logger
  template:
    metadata:
      labels:
        app: fluentd-logger
    spec:
      tolerations:          # also run on control-plane nodes
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
      containers:
        - name: fluentd
          image: fluent/fluentd:v1.16
          resources:
            limits:
              memory: 200Mi
          volumeMounts:
            - name: varlog
              mountPath: /var/log
      volumes:
        - name: varlog
          hostPath:
            path: /var/log

Handy commands

  • kubectl get daemonset -n logging — list DaemonSets and desired/current/ready counts.
  • kubectl describe ds fluentd-logger -n logging — inspect scheduling & events.
  • kubectl get pods -o wide -l app=fluentd-logger — see one pod per node.
  • kubectl rollout status ds/fluentd-logger -n logging — track a rolling update.
One-line answer: A DaemonSet has no replicas field — it schedules a pod onto every matching node, uses hostPath or host resources to work at the node level, and relies on tolerations/nodeSelector to control exactly which nodes get a pod.
