What is a ConfigMap?

A simple place to keep your app's settings — outside the code

A ConfigMap is where you keep an app's settings as key-value pairs, so they live outside your container image. That way you can change a setting without rebuilding the image or touching the code.

🐳 Like Docker env vars

  • In Docker you pass settings with -e / ENV.
  • In Kubernetes, a ConfigMap does the same job — it feeds settings into your container.

🎯 Why bother?

  • No more hardcoded values in the app.
  • Values often change per environment — dev, test, prod.
  • One image runs everywhere, just with a different ConfigMap.
In one line: A ConfigMap keeps your settings separate from your code, so the same app can run anywhere just by swapping its configuration.

ConfigMap vs Secret

Same idea, but one is for safe data and one is for sensitive data

Both store key-value data. The difference is what kind of data goes in each.

✅ ConfigMap — safe data

  • For non-confidential settings.
  • Examples: API endpoints, URLs, log level, feature flags.
  • Stored as plain text — no encryption.

🔒 Secret — sensitive data

  • For confidential data.
  • Examples: usernames, passwords, tokens, keys, ports.
  • Adds encryption & stricter access.
Important: A ConfigMap gives you no security or encryption. If the data is secret, use a Secret. Also, a ConfigMap can hold only 1 MiB — for anything bigger, mount a volume or use a database / file service.

Ways to Create a ConfigMap

Two styles: quick commands, or a YAML file you can save

1. With a command (kubectl create configmap)

From literals

  • Type values right in the command.
kubectl create configmap app-config \
  --from-literal=LOG_LEVEL=debug

From a file

  • Read values from a file.
kubectl create configmap app-config \
  --from-file=app.properties

From an env file

  • Each KEY=value line becomes a key.
kubectl create configmap app-config \
  --from-env-file=config.env

2. With a YAML file (declarative)

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: debug
  APP_MODE: prod
# save it, then run: kubectl apply -f configmap.yaml
Which one? Commands are great for a quick test. A YAML file is better for real projects — you can save it in Git and reuse it.

Using a ConfigMap in a Pod

Two ways to get the settings into your container

As environment variables

containers:
  - name: web
    image: nginx
    # bring in ALL keys
    envFrom:
      - configMapRef:
          name: app-config
    # or just ONE key
    env:
      - name: LOG_LEVEL
        valueFrom:
          configMapKeyRef:
            name: app-config
            key: LOG_LEVEL

As files (mounted volume)

containers:
  - name: web
    image: nginx
    volumeMounts:
      - name: config-vol
        mountPath: /etc/config
volumes:
  - name: config-vol
    configMap:
      name: app-config
# each key shows up as a file in /etc/config
Good to know: Files mounted from a ConfigMap update on their own when the ConfigMap changes. Environment variables do not — you have to restart the Pod.

Using Many ConfigMaps in One Pod

Yes — a Pod can pull from several ConfigMaps, and even pick single keys

A Pod isn't limited to one ConfigMap. You can attach several, and you can also grab just the keys you want from each.

Attach several ConfigMaps

envFrom:
  - configMapRef:
      name: app-config
  - configMapRef:
      name: db-config
  - configMapRef:
      name: feature-flags

Pick keys from different ones

env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: LOG_LEVEL
  - name: DB_HOST
    valueFrom:
      configMapKeyRef:
        name: db-config
        key: DB_HOST
Watch out: If two ConfigMaps have the same key, the last one listed wins. Also, all ConfigMaps must be in the same namespace as the Pod, or the Pod won't start (unless you mark them optional: true).

Handy commands

  • kubectl get configmaps — list them.
  • kubectl describe configmap app-config — see its keys and values.
  • kubectl create configmap app-config --from-literal=KEY=value — quick create.
  • kubectl edit configmap app-config — edit it.
  • kubectl delete configmap app-config — delete it.
Remember: ConfigMaps are plain text. Never put passwords, API keys, or certificates in them — use a Secret instead.

What is a Secret?

Like a ConfigMap, but built for sensitive data

A Secret stores sensitive key-value data — passwords, tokens, API keys, TLS certificates — outside your container image. It works just like a ConfigMap, but Kubernetes treats the data more carefully.

🔒 Why not a ConfigMap?

  • ConfigMaps store everything in plain text.
  • Secrets are stored base64-encoded and can be encrypted at rest in etcd.
  • Access can be locked down with RBAC.

⚠️ Base64 is NOT encryption

  • Base64 only encodes — anyone can decode it.
  • Real protection comes from encryption at rest + RBAC.
  • Never commit raw Secret YAML with values to Git.
In one line: Use a Secret for anything confidential. It behaves like a ConfigMap, but adds encoding, optional encryption at rest, and tighter access control.

Ways to Create a Secret

Quick commands, or a YAML file — same styles as ConfigMaps

1. With a command (kubectl create secret)

From literals

  • Type values right in the command.
kubectl create secret generic db-secret \
  --from-literal=DB_USER=admin \
  --from-literal=DB_PASS=s3cr3t

From a file

  • Read values from a file.
kubectl create secret generic tls-secret \
  --from-file=./creds.txt

For TLS

  • Dedicated type for certs & keys.
kubectl create secret tls my-tls \
  --cert=tls.crt --key=tls.key

2. With a YAML file (declarative)

apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:                 # values must be base64-encoded
  DB_USER: YWRtaW4=       # "admin"
  DB_PASS: czNjcjN0       # "s3cr3t"
# Tip: use stringData: to put plain text; Kubernetes encodes it for you
Handy: stringData: lets you write plain-text values — Kubernetes base64-encodes them automatically, so you don't have to run base64 by hand.

Using a Secret in a Pod

Same two ways as a ConfigMap — env vars or mounted files

As environment variables

containers:
  - name: web
    image: nginx
    # bring in ALL keys
    envFrom:
      - secretRef:
          name: db-secret
    # or just ONE key
    env:
      - name: DB_PASS
        valueFrom:
          secretKeyRef:
            name: db-secret
            key: DB_PASS

As files (mounted volume)

containers:
  - name: web
    image: nginx
    volumeMounts:
      - name: secret-vol
        mountPath: /etc/secret
        readOnly: true
volumes:
  - name: secret-vol
    secret:
      secretName: db-secret
# each key shows up as a file in /etc/secret
Good to know: Mounted Secret files are decoded automatically — the container reads plain values. Like ConfigMaps, file mounts refresh on change; env vars need a Pod restart.

Secret Types & Quick Reference

Common Secret types and the commands worth remembering

TypeUsed for
OpaqueDefault — arbitrary user-defined key-value data
kubernetes.io/tlsTLS certificate + private key (tls.crt / tls.key)
kubernetes.io/dockerconfigjsonPrivate registry credentials for pulling images
kubernetes.io/basic-authUsername & password pair
kubernetes.io/service-account-tokenToken for a ServiceAccount

Handy commands

  • kubectl get secrets — list them.
  • kubectl describe secret db-secret — see keys (values stay hidden).
  • kubectl create secret generic db-secret --from-literal=KEY=value — quick create.
  • kubectl get secret db-secret -o jsonpath='{.data.DB_PASS}' | base64 -d — decode a value.
  • kubectl delete secret db-secret — delete it.
Remember: Secrets are only base64-encoded by default, not encrypted. Turn on encryption at rest, restrict access with RBAC, and keep raw Secret values out of Git.
