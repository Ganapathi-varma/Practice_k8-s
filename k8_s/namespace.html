Why Use Namespaces?

Dividing one physical cluster into multiple virtual clusters

🧩Resource Isolation

  • Separate environments (dev, staging, prod) or teams in one cluster.
  • Workloads don't step on each other.

🏷️Scope for Names

  • Resource names only need to be unique within a namespace.
  • frontend can exist in both dev and prod.

🔐Access Control (RBAC)

  • Grant permissions scoped to a namespace.
  • Team A can't touch Team B's resources.

📊Resource Quotas

  • Limit CPU, memory & object counts per namespace.
  • One team can't exhaust the whole cluster.
When NOT to use them: Namespaces are not a hard security boundary for isolating different customers — use separate clusters for that. Also, cluster-wide resources like Nodes and PersistentVolumes are not namespaced.

Kubernetes: Default Namespaces

Four namespaces every cluster creates out of the box & what they are for

default

  • The namespace where your resources go if you don't specify one.
  • Meant for user workloads during learning / quick testing.
  • Best practice: create your own namespaces for real apps instead of using default.

kube-system

  • Holds objects created by the Kubernetes system itself.
  • Runs control-plane & core components: kube-dns/CoreDNS, kube-proxy, CNI, metrics-server.
  • Do not deploy your own apps here — avoid interfering with cluster internals.

kube-public

  • Created automatically and is readable by all users (including unauthenticated).
  • Mostly reserved for cluster-wide public info.
  • Holds a cluster-info ConfigMap used during bootstrap / join.

kube-node-lease

  • Holds Lease objects, one per node, for node heartbeats.
  • Lets the control plane detect node health efficiently & at scale.
  • Lightweight leases replace heavier status updates, improving performance.
One-line answer for interview: Kubernetes ships with four namespaces — default (your resources when none is given), kube-system (control-plane & system components), kube-public (publicly readable cluster info), and kube-node-lease (per-node heartbeat leases for node health).

Purpose at a glance + useful commands

Handy commands

  • kubectl get namespaces — list all namespaces (you'll see these four by default).
  • kubectl get pods -n kube-system — view system/control-plane pods.
  • kubectl get configmap cluster-info -n kube-public — see public cluster info.
  • kubectl get leases -n kube-node-lease — see one heartbeat lease per node.
  • kubectl create namespace my-app — create your own namespace for real workloads.
Remember: default = your stuff · kube-system = cluster internals · kube-public = readable by all · kube-node-lease = node heartbeats. For production, put apps in your own namespaces, not in default or kube-system.

Kubernetes Namespaces — Interview Reference

Sample Namespace YAML

Creating a namespace with a quota and limit range

Basic namespace

apiVersion: v1
kind: Namespace
metadata:
  name: dev
  labels:
    environment: development
    team: backend

Deploy into a namespace

metadata:
  name: web
  namespace: dev  # places it in dev

With a ResourceQuota

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"

Useful commands

  • kubectl apply -f namespace.yaml — create from a file.
  • kubectl create namespace dev — create quickly without a file.
  • kubectl get pods -n dev — run a command against a namespace.
  • kubectl config set-context --current --namespace=dev — set a default namespace.
Tip: Separate objects in a single YAML file with --- so a Namespace, ResourceQuota, and LimitRange can be applied together in one kubectl apply.

What Happens If You Delete a Namespace?

A cascading, irreversible delete — everything inside goes with it

The delete process

  • kubectl delete namespace <name> puts it into a Terminating phase.
  • Kubernetes deletes all namespaced resources inside it.
  • Finalizers run to clean up before objects are removed.
  • Once empty & all finalizers clear, the namespace itself is deleted.

❌ Deleted (namespaced)

  • Pods, Deployments, StatefulSets, DaemonSets, ReplicaSets
  • Services, Ingresses, NetworkPolicies
  • ConfigMaps, Secrets, ServiceAccounts
  • PVCs & Roles / RoleBindings in that namespace

✅ Survives (cluster-scoped)

  • Nodes, PersistentVolumes (the PV object)
  • ClusterRoles / ClusterRoleBindings
  • StorageClasses, CRDs, other Namespaces

Important side effects

  • Data loss depends on the PV's reclaim policy: Delete wipes the backing volume; Retain keeps the data (reclaim it manually).
  • Deleting LoadBalancer Services removes the cloud load balancer they provisioned.
  • Cannot be undone — no trash/restore. Recovery needs backups (e.g. Velero) or manifests in Git.
⚠️ Warning: Deleting a namespace deletes everything inside it. Never delete kube-system — it breaks the cluster. If a namespace is stuck in Terminating, a leftover finalizer is usually the cause. Always double-check your context with kubectl config current-context first.
