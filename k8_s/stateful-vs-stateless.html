Kubernetes: Stateful vs Stateless Applications

Core concept in Kubernetes & cloud-native architecture

Stateless

  • Does not store past data — each request is independent.
  • No memory of previous interactions; nothing is saved after the request completes.
  • Relies on non-persistent data — data is lost when the pod, node, or cluster stops.
  • If a pod is deleted, there is no guarantee the data is preserved.
  • Non-persistent data is mainly used for logging (system logs, container logs, etc.).
  • Can be deployed as a set of identical replicas; each replica handles requests independently without coordinating with others.
  • Deployed in Kubernetes using a Deployment.

Stateful

  • Stores and remembers past data across requests and restarts.
  • Uses persistent storage — data survives pod/node restarts.
  • Each replica has a stable, unique identity and its own storage.
  • Replicas are not interchangeable; order and identity matter.
  • Used to solve the data-loss problem of stateless apps.
  • Examples: databases, message queues, caches (MySQL, Kafka, Redis).
  • Deployed in Kubernetes using a StatefulSet + PersistentVolume.
One-line answer for interview: A stateless application keeps no record of previous requests — any replica can serve any request. A stateful application remembers data and needs persistent storage and a stable identity.

Why a Deployment is called "stateless"

  • A Deployment won't save past data — it can't store data permanently.
  • If you delete a pod, there is no guarantee the data is kept.
  • It depends on non-persistent data (removed when pod/node/cluster stops).
  • To avoid this problem, we use stateful applications (StatefulSet + persistent storage).
Remember: Stateless = no memory, scale freely, use Deployment. Stateful = has memory, needs persistent storage + stable identity, use StatefulSet.

Scaling Replicas: Deployment vs StatefulSet

What happens when you scale up or scale down

Deployment (Stateless)

  • Scale up: new pods created all at once, in parallel — no ordering.
  • Pods get random names (e.g. myapp-7d8f-xk2p9).
  • Every pod is identical & interchangeable — any pod serves any request.
  • They share nothing: no stable identity, no dedicated storage.
  • Scale down: pods killed in any order; local data is lost.
  • Scaling is fast & easy — pods don't coordinate or own data.

StatefulSet (Stateful)

  • Scale up: pods created one at a time, in order: db-0 → db-1 → db-2.
  • Each pod waits until the previous one is Running & Ready.
  • Pods get stable names (ordinal index) and keep them.
  • Each pod has its own PersistentVolume bound to its identity.
  • Scale down: pods removed in reverse order (highest first), one at a time.
  • The PersistentVolume is NOT deleted — data survives & reattaches on scale-up.

One-line answer: In a Deployment, scaling adds/removes interchangeable pods in parallel with no data preserved. In a StatefulSet, pods scale one at a time in order, each keeping its own stable identity and PersistentVolume, so data survives.
